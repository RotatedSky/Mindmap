# 开发工作流

本文档定义本仓库（纯前端、Node 内置测试）的开发流程，适用于功能开发、缺陷修复、重构与技术替换。opencode 推进任何开发任务时必须遵循以下循环：

```
方案设计 → 开发 → 测试 → 问题修改 → (回归测试) → 完成
```

每个阶段有明确的产出与验收点；测试阶段暴露的问题必须进入"问题修改"阶段闭环，不得跳过或绕过。

---

## 阶段 1：方案设计

目标：动手写代码前明确需求、影响面与验收标准。

1. **明确需求**：从用户描述中提取功能点、边界情况与验收标准；不明确的细节向用户确认，不自行假设。
2. **识别任务类型**，决定关注点与影响面：
   - 功能开发：新增逻辑与既有行为的交互
   - 缺陷修复：先写出最小复现用例，定位根因后再改；修复后补回归用例
   - 重构/技术替换：行为等价优先，影响面检查（见下）必须逐项过，替换类任务需明确新旧行为差异清单
3. **梳理影响面**：列出涉及模块与数据流，重点排查：
   - 数据模型（`model.js`）：新增字段是否影响序列化、撤销/重做、剪贴板
   - 存储兼容（`storage.js` / 导出 JSON）：旧数据能否加载，格式变更是否向后兼容
   - 渲染与布局（`render.js` / `layout.js`）：几何测量、文本测量桩的一致性
   - 导出（`exporter.js`）：复用渲染逻辑的改动会自动传播
4. **确定方案**：选择最小改动方案，符合现有代码约定（IIFE、`window.MM`、零依赖）。
5. **输出**：
   - 简短的设计说明（改动点、影响面、测试策略）
   - `todowrite` 任务清单（方案设计/开发/测试/问题修改 每阶段一项）

## 阶段 2：开发

1. 按 todo 逐项实现；完成后暂停提交，汇总改动向用户汇报，经用户 review 确认后才可提交（不默认提交）。
2. 遵循代码约定：
   - 零依赖；模块为 IIFE，导出到 `window.MM`
   - 不添加代码注释（除非用户要求）
   - 数据格式变更必须向后兼容
3. 优先为可测逻辑编写测试用例（测试先行或同步编写），新增公开 API 必须有用例覆盖。
4. 引入外部库（vendor）时的检查项：
   - 许可证：MIT/BSD 等宽松许可，来源与版本写入 vendor 目录说明
   - 资源：放入 `vendor/` 随仓库提交，体积有预算（增量为百 KB 级须向用户说明）
   - 兼容性：库要求与目标浏览器范围一致（现代浏览器、排除 IE）
   - 异步初始化：字体/资源加载需处理就绪状态与降级路径，避免竞态（如测量缓存须在字体就绪后写入）
   - 沙箱不可用：测试环境中库行为不可用时的 fallback 路径必须有用例覆盖，且 fallback 不得改变可测逻辑的语义

## 阶段 3：测试

1. 运行全量测试：`npm test`；语法检查：`node --check js/<file>.js`。
2. 新增用例放在对应模块的 `test/<module>.test.js`，遵循沙箱规则（见"测试用例常见错误"）。
3. 几何 / 布局算法变更（外框、连线、测量相关）必跑随机回归：`node test/fuzz-frames.js`（两 seed × 5000 runs × 6 方向）。fuzz 失败会自动留存现场到 `test/failures/`（已 gitignore），用 `node test/repro.js <现场.json> [布局方向]` 一键复现并打印全部几何 / pad / pill 检查值，无需手工构造复现用例。
4. 浏览器冒烟：
   - 触发条件（满足任一即必须冒烟）：DOM 重交互（拖拽、菜单、输入框）、Canvas/SVG/foreignObject 渲染、导出下载、外部库（如 KaTeX）在真实浏览器中的行为
   - 优先用自动化冒烟：`python tools/smoke_ui.py`（Playwright，覆盖右键菜单交互与外框几何断言；首次使用需 `pip install playwright` + `playwright install chromium`），或 `--headed` 观察真实交互
   - 自动化覆盖不到的再手动冒烟；冒烟结论写入该次任务的结果说明，注明浏览器与验证的功能点；冒烟暴露的问题转入阶段 4 闭环

## 阶段 4：问题修改（闭环）

测试失败时，先分类再处理，禁止直接绕过：

| 分类 | 判定 | 处理 |
|------|------|------|
| A. 测试用例错误 | 产品代码行为正确（人工核对或对照既有行为），期望值/写法错误 | 修正测试：期望值、断言方式或环境适配 |
| B. 产品代码缺陷 | 行为确实不符合需求或自相矛盾 | 修复代码，保留并更新测试以覆盖该缺陷 |
| C. 环境/工具问题 | 失败与产品行为无关（沙箱限制、Node 版本差异等） | 适配测试环境，必要时向用户说明 |

**铁律**：
- 禁止为通过测试而删除断言、弱化断言、跳过测试。
- 判断不明确时（A vs B），与用户确认，不得擅自选择。
- 修复后必须回归全量测试，并核对受影响用例。

### 测试用例常见错误（本仓库典型问题）

1. **跨 realm 对象断言**：vm 沙箱中创建的对象与宿主断言库原型不同，`assert.deepEqual/strict` 会报 "Values have same structure but are not reference-equal"。应改用 shim 导出的 `sameJSON()`（JSON 比较）或逐字段断言。
2. **期望值推算错误**：文本测量桩为确定性值——ASCII 8px/字符，CJK（码点 > U+2FFF）16px/字符；换行/截断的期望宽度按此推算，不要凭感觉。
3. **根对象引用过期**：撤销/重做、deserialize 会替换 `state.root`，旧引用指向已脱离树的节点。断言前重新读取 `mm.Model.root`。
4. **沙箱共享状态污染**：模块级状态（如 `state.seq`、metricCache）跨用例残留；每个用例必须通过 `fresh()` 创建独立沙箱，不得在用例间共享。
5. **示例树干扰**：`mm.Model.root` 默认是含 4 个子树的示例树；需要干净根时用 `createNode` + `replaceRoot`。
6. **事件与定时器**：搜索测试需先 `M.Search.init()` 再用 `singletonEl.dispatch()` 触发；`M.Storage.save()` 是 400ms 防抖，用 `timers.tick(400)` 推进假定时器。
7. **假阳性（测试通过但没覆盖缺陷）**：断言过弱或漏测关键路径。新增用例应能区分正确与错误实现——不确定时先确认用例在缺陷代码上会失败。
8. **修改共享对象而未生效**：`setup()` 返回的 `mm` 即沙箱内真实 `window.MM` 引用，直接在其上挂桩（如 `mm.Theme = ...`、`mm.Render = ...`）会生效；不要创建副本再改。

## 完成标准（Definition of Done）

- [ ] `npm test` 全量通过（含新增用例）
- [ ] 改动文件 `node --check` 通过
- [ ] 改动最小化且符合代码约定；数据格式变更向后兼容
- [ ] 重构/技术替换类任务保持行为等价（既有测试全通过，行为差异已向用户说明）
- [ ] 无遗留 TODO/FIXME 或已向用户说明
- [ ] 功能/交互变更同步更新 `README.md` 功能说明与工具欢迎页面（`js/app.js` 的 `showWelcome()` 提示文案），两者与行为一致
- [ ] 改动经用户 review 确认后再提交（默认不自动提交）
- [ ] 提交信息按 `docs/commit-message-template.md` 模板填写（含 TEST 行，如需提交）
